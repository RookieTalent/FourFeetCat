# Harness 设计：用门禁保证每个功能符合预期

这门课的开发方式有一个前提：**写代码的是 AI，不是人**。人盯着 AI 一行行看 diff，既看不动，也不可靠。那"这个功能做对了没有"靠什么保证？靠门禁。

一句话（第 6 节讲过，这里展开成完整设计）：**SDD 给目标，Harness 给边界。** Spec-Kit 的 spec 写清楚"要做成什么样"，Harness 负责判"做出来的东西符不符合"——不靠人盯，靠判卷。

## 一、为什么 AI 写码尤其需要门禁

传统开发里，人是实现者，验收靠 code review + 测试。到了 AI 写码，角色变了：

- **AI 会自信地写错**。AI 产出的代码看起来工整、注释齐全，错得也很自信。靠肉眼审海量 diff，漏判是必然的。
- **AI 会"顺手"改不该改的**。类名、配置键、表列名、已定的方法签名——AI 为了让代码跑通，很乐意把字面量"修正"掉，而那正是上一节定下的契约。
- **AI 会让测试变绿**。最省事的修法不是修实现，而是删断言、`@Disabled`、放宽阈值——门禁本身成了被"优化"的对象。

所以人的角色从**审代码**变成**审边界**：把"什么算对"提前写成机器可判的规则，让机器去判；机器判不了的，强制 AI 停下来问人。这就是总纪律：

> **能机器判的绝不留给人，机器判不了的绝不自行发挥。**

## 二、三类防线

### 硬门禁：机器判，不过不放行

| 门禁 | 判什么 |
|------|--------|
| 单测套件（harness 主体） | 实现对不对——路由、校验、审计、翻译，mock 掉外部 IO |
| `mvn clean verify` 全绿 | 构建级质量——P3C、SpotBugs、FindSecBugs、PMD 静态检查全过 |
| 交付物存在性核对 | 课件"本节交付物"清单里的类、表、配置，逐项 ls/grep 确认存在 |
| 前序节全部测试回归绿 | 本节的改动没把前面各节做坏（跨节契约证据） |

硬门禁没有商量余地：不过就是没完成，不许绕。`mvn clean verify` 不绿，不管功能看起来多能跑，都不算交付。

### 软门禁：机器判不了，停下问人

以下六种情况，AI **立即停下、向用户报告、等确认后继续**，不得自行决定：

1. 要创建"本节交付物"清单之外的任何**对外概念**（public 类型、配置键、数据表、REST 路径、Profile 字段）——概念扩散是架构漂移的起点；
2. 要修改任何**已定字面量**（类名、方法签名、配置键、表列名、端点路径）——它们是前序节的契约，改一个字就是违约；
3. **课件与技术方案冲突**——两份权威打架，只有人能裁决；
4. 要修改**前序节交付的公共接口**（当节课件明确列为"改造点"的除外）——下游都在用；
5. **第三方 API 在本地依赖中核实不到**——教程里的名字只是示意，接不接得进来要拿证据；
6. 要新增 **plan 未列明的第三方依赖**——依赖是审计项，不是顺手的事。

这六条的共性：**机器当时判不了对错，但事后追责的代价极高**。停下来问一句，是最便宜的保险。

### 反作弊

- 不得删断言、不得 `@Disabled`、不得放宽阈值让测试变绿。
- 实现错了修实现；认为测试本身错了，停下报告，不自行改卷。
- **未全绿不得宣称完成。**

## 三、Harness 的主体是测试，怎么分层

分层判据只有一条：**要不要碰真实网络。**

- **单测（默认全跑）**：把 ChatModel、外部服务全部 mock 掉，不花一分钱、不依赖网络，秒级跑完。路由对不对、审计落没落、工具格式翻得对不对，全在这里判。这是 harness 的主体，也是 CI 门禁。
- **集成冒烟（打 `@Tag("integration")`，本地手动跑）**：真调一次模型，验证"key 对、依赖对、真的通"。CI 里默认跳过——不能让外部 API 的可用性变成自己流水线的可用性。

以第 16 节为例：`ProviderServiceTest`（mock 两个 ChatModel，判路由和审计）是单测；`ProviderSmokeIT`（读真 key、真调一次、断言 `llm_calls` 多了一条 `success=true`）是集成冒烟。前者机器判、门禁化；后者交给人手动跑。

单测里还有个讲究：**建表要走那份手工脚本**（测试里执行 `schema.sql`），不要让 Hibernate 自动建——不然测试绿了、生产上跑真脚本时列名对不上，白测。

## 四、关键回归测试：每个"坑"钉一个测试

课件的"想清楚"部分会点名几个坑——那是架构决策的浓缩。**每个坑都应该有一个对应的回归测试**，坑才算被永久钉死，后来的人改不回去。

第 16 节的三个例子（也是整套方法的样子）：

| 坑 | 测试 | 钉死它的断言 |
|----|------|------------|
| 坑一：多 provider 分不清谁是谁 | 按名路由不串台 | `verify(kimi, times(1)).call(any())` 且 `verify(deepseek, never()).call(any())`——deepseek 一次都没被碰，是"不串台"的直接证据 |
| 坑二：Spring AI 自作主张执行工具 | 带工具 schema 调用时自动执行已关闭 | `assertFalse(captor.getValue().autoExecuteTools())`——一旦有人改回自动执行，这里立刻红 |
| 最容易漏的：失败不留痕 | 调用失败审计必须落 `success=false` | 断言的不是"没抛异常"，而是"**抛了异常并且审计先落了账**"——`success=false` + 错误原因入库 |

第三个例子值得多说一句：失败路径的审计是最容易被漏掉的。只记成功不记失败，一次真实事故在系统里就完全没留下痕迹，"可审计"这个卖点就打了折扣。

## 五、Harness 先行

测试不是写完实现再补的，是**在实现之前（或同时）定下来**的。落到流程里：

- 课件每个模块的"验收 harness"部分就是测试清单，它先于代码存在；
- 任务清单里，测试任务先于或伴随对应的实现任务；
- **任务级 DoD**：实现与测试一起落地，跑该模块测试，红了当场修，不攒到最后。

顺序反了会怎样？先写实现再写测试，测试会不自觉地照着实现的样子写——那不是判卷，是抄答案。

## 六、节级判卷：六项证据 DoD

一节课做完，宣布"完成"前要凑齐六项证据，逐项写进验收报告：

1. `mvn clean verify` 全绿（含 P3C/SpotBugs/FindSecBugs/PMD），贴关键输出——**构建判过了吗**；
2. 课件 harness 映射表的每个测试类存在且非空，关键回归测试逐个对号——**判卷的卷子齐了吗**；
3. "本节交付物"逐项存在性核对——**答应的东西都在吗**；
4. 前序节全部测试回归绿——**前面的节没被我改坏吧**；
5. 全局不变量逐条自查（涉外 IO 过沙箱、审计成败都落库、无明文 key、`session_id` 拼接只在 SessionManager、无异步模型、无 Spring AI 自动工具执行路径）——**整个系统的底线守住了吗**；
6. 剩余人工项清单（见下节）——**还有什么要人过**。

验收报告之外再给一份变更总结（改动点 / 重点 review 清单 / 如何验证的命令块），这是给 reviewer 的导读——判卷归机器，导读给人看。

## 七、机器判不了的：人工项清单

harness 跑绿之后，总有机器覆盖不到或不值得自动化的部分，明确列出来交给人，常见的如：

- 依赖真实可用：目标 starter 在锁定 BOM 里**能下载、能解析**（`mvn dependency:tree` 看一眼）；
- 集成冒烟真跑过：配真 key，`ProviderSmokeIT` 通过、拿到过真实响应；
- 凭证卫生：`grep` 代码和配置，搜不到明文 key。

一句话收尾：**harness 已判卷，这几项等你人工过。** 机器把能判的都判完，剩下的清清楚楚交给人——这才是"符合预期"的完整定义。
