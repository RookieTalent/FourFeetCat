## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多轮"想—做—看"直到把事办成 (Priority: P1)

用户问一句"看看今天天气，帮我决定穿什么"。模型第一轮要求调用查询工具，系统执行后把结果回填进对话，第二轮模型据此给出穿搭建议并收尾；用户拿到的是最终答复，不是"我想调个工具"这种半成品。若模型第一轮就能直接回答，则一轮即收尾，不做多余往返。

**Why this priority**: 这是本模块存在的全部理由——没有这个循环，Agent 与普通问答机器人没有任何区别；其余能力（审计、上下文组装、编排）都挂在这条主链上。

**Independent Test**: 用替身模型（不回真网络）跑两种剧本——首轮要求调用工具、次轮给最终答复，验证工具被执行、结果进入下一轮、最终答复被返回；首轮直接给答复，验证模型只被调一次。

**Acceptance Scenarios**:

1. **Given** 模型首轮要求调用某工具，**When** 处理这条用户消息，**Then** 该工具被系统执行一次，执行结果被回填进对话并进入下一轮，模型再次被调用。
2. **Given** 模型某轮响应中没有任何工具调用要求，**When** 处理这条用户消息，**Then** 该轮响应文本作为最终答复返回，循环结束。
3. **Given** 一次响应里包含多个工具调用要求，**When** 处理这条响应，**Then** 这些工具按顺序逐个执行（不并行），每个结果都回填进对话。

---

### User Story 2 - 转不下去时强制收尾，绝不挂死 (Priority: P2)

模型反复要求调用工具、迟迟不给最终答复。系统不会无限转下去：转满上限次数后强制结束，并给出明确的收尾信号，让上层知道这次是被上限截断的，而不是拿到了正常答复。

**Why this priority**: 这是循环最容易出的事故——没有上限的一次模型抽风就是一次线上挂死或一次账单失控。

**Independent Test**: 替身模型每一轮都要求调用工具、永不收敛，验证模型调用次数恰好等于上限次数（一轮不多），且返回内容明确表示因达到上限而结束。

**Acceptance Scenarios**:

1. **Given** 上限配置为 10、模型每轮都要求调用工具，**When** 处理这条用户消息，**Then** 模型恰好被调用 10 次，返回内容含"达到最大轮数"语义的收尾信号。
2. **Given** 上限配置为 3，**When** 处理同一条用户消息，**Then** 模型恰好被调用 3 次——上限可配置、按配置生效。

---

### User Story 3 - 每次工具调用无论成败都留痕 (Priority: P2)

某次工具执行失败（参数错、外部服务不可用）。运维事后追查：审计记录里能找到这次调用，成败标记为失败并带着原因。执行成功时同样记账：调了哪个工具、传了什么参数、拿到什么结果、耗时多久。每一轮的模型响应与工具结果也都被累积进会话状态，使下一轮能接上前一轮、事后能复现整条链路。

**Why this priority**：没有工具调用的审计，一次失败的工具调用在系统里就没有任何痕迹；没有累积，下一轮模型看到的上下文是残缺的、事后也无法复现。

**Independent Test**: 工具执行成功与失败各跑一次，验证审计记录各一条、失败记录带原因；跑一轮"模型要求调工具"的剧本，验证会话状态里同时含该轮模型响应与工具执行结果。

**Acceptance Scenarios**:

1. **Given** 工具执行成功，**When** 执行返回，**Then** 审计记录新增一条成功标记为真、含工具名、调用参数、结果与耗时。
2. **Given** 工具执行失败，**When** 执行返回，**Then** 审计记录新增一条成功标记为假、错误信息含失败原因；失败信息被回填进对话让模型能接着处理，而不是被静默吞掉。
3. **Given** 处理完一条用户消息，**When** 查会话状态，**Then** 里面含用户消息、每轮的模型响应、每次工具执行的结果。

---

### User Story 4 - 每轮上下文按固定顺序组装、超长自动截断 (Priority: P2)

每次请求模型前，系统把要说的话按固定顺序拼好：角色设定与启动信息（末尾附上当前日期时间——模型自己不知道今天几号）、长期记忆（未启用则跳过）、最近的对话历史（只留最近若干轮，默认 20 轮，超出部分丢弃）、当前可用工具说明。长期记忆是跨会话累积的东西、对话历史是这一次对话的往来记录，两者是两回事，拼接时各归各位。

**Why this priority**: 顺序错了或历史不限长，模型会拿到错位的上下文；历史无限堆叠则会撑爆上下文窗口——这是循环的第二个坑。

**Independent Test**: 构造一段超过上限的对话历史，验证注入的历史被截断到上限轮数；构造角色设定与启动信息，验证四部分顺序稳定、末尾带当前日期时间。

**Acceptance Scenarios**:

1. **Given** 对话历史超过上限轮数，**When** 组装本轮上下文，**Then** 注入的历史只保留最近上限轮数，更早的被丢弃。
2. **Given** 任一 Profile，**When** 组装本轮上下文，**Then** 四部分按"角色与启动信息 → 长期记忆 → 对话历史 → 工具说明"的固定顺序出现，且角色与启动信息部分末尾含当前日期时间。
3. **Given** 未启用长期记忆，**When** 组装本轮上下文，**Then** 长期记忆部分被跳过，不报错、不占位。

---

### User Story 5 - 一次处理的编排：当前 Agent 可见、绝不泄漏 (Priority: P3)

一次消息处理由统一入口编排：进门时记住"这次是哪个 Agent 在处理"（工具执行时需要知道当前 Agent 的配置），结束时——无论正常返回还是中途抛异常——都把这个记忆清掉；处理产物在结束时被持久化。三种触发源（终端、HTTP、定时）都走这一个入口，不各自实现循环。

**Why this priority**: 这是最容易漏、也最难查的一类 bug——单请求测试永远不报错，只在并发复用线程时串号，把 A 的配置用到了 B 身上。

**Independent Test**: 处理过程中读到的"当前 Agent"与传入的一致；让处理过程抛异常，验证异常上抛后该记忆仍被清除；处理结束后验证会话状态被持久化。

**Acceptance Scenarios**:

1. **Given** 一次正常处理，**When** 处理进行中，**Then** 执行线程上能读到本次的 Agent 配置；**When** 处理结束，**Then** 该记忆被清除。
2. **Given** 处理过程中抛出异常，**When** 异常向上抛出，**Then** 该记忆同样被清除，不会留给复用同一线程的下一条请求。
3. **Given** 一次处理结束，**When** 处理返回，**Then** 会话状态已被持久化（不是只活在内存里）。

---

### User Story 6 - 启动上下文现读现用、缺失不静默 (Priority: P3)

用户改完启动信息文件（项目说明、人格、用户偏好）或能力包描述，希望下一轮立即生效，不用重启。系统每次组装上下文都重新读文件、不缓存。被显式引用的文件缺失时报错，启动信息文件缺失时至少告警——静默跳过会造成"人格悄悄丢了"这种最难查的软故障。

**Why this priority**: 缓存带来的"改了不生效"和静默跳过带来的"悄悄丢人格"，都是排查成本极高的软故障，必须在设计时就定死。

**Independent Test**: 读一次内容 → 改文件 → 再读一次，验证第二次读到新内容；引用一个不存在的文件验证报错；缺一个启动信息文件验证至少告警且不中断。

**Acceptance Scenarios**:

1. **Given** 启动信息文件内容被修改，**When** 下一次组装上下文，**Then** 读到的是新内容（两次组装结果不同，证明无缓存）。
2. **Given** 配置里显式引用了某个能力包/文件但实际不存在，**When** 组装上下文，**Then** 得到清晰报错，不静默跳过。
3. **Given** 某个启动信息文件缺失，**When** 组装上下文，**Then** 记录告警并继续，不阻断本次处理。

### Edge Cases

- 模型响应只有工具调用要求、没有文本：不作为最终答复返回，继续下一轮。
- 工具执行抛异常：异常不得被吞——审计记失败并带原因，失败结果回填对话，循环继续（由模型决定下一步），循环本身不因工具失败而崩。
- 最大轮数配置缺失或非法：使用默认值 10。
- 历史轮数超出上限且边界正好等于上限：不截断（只在超过时截断）。
- 首次处理、对话历史为空：正常进入循环，不报错。
- 启动信息文件清单为空：不报错，跳过启动信息部分。
- 处理中持久化失败：异常上抛，且"当前 Agent"记忆仍被清除。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在收到用户消息后进入循环：组装当轮上下文 → 请求模型 → 观察响应；响应中不含工具调用要求时，MUST 返回该响应文本作为最终答复并结束循环。
- **FR-002**: 循环 MUST 有可配置的最大轮数，默认 10；达到上限时 MUST 强制结束并返回明确的收尾信号，MUST NOT 无限循环或静默挂住。
- **FR-003**: 响应中的工具调用要求 MUST 由系统按顺序逐个执行，执行结果 MUST 回填上下文后进入下一轮；系统 MUST NOT 存在第二条自动执行工具的路径。
- **FR-004**: 每一轮的模型响应与每次工具执行结果 MUST 累积进会话状态，使下一轮能接续、事后可复现。
- **FR-005**: 每轮发给模型的上下文 MUST 按固定顺序由四部分组成：角色设定与启动信息（末尾附当前日期时间）、长期记忆（未启用则跳过）、最近 N 轮对话历史（超出上限则截断，默认 20 轮）、当前可用工具说明；长期记忆与会话历史 MUST 分别取值，不得混同。
- **FR-006**: 每次工具执行 MUST 落一条审计记录：会话、工具名、调用参数、执行结果、成败、失败原因、耗时；失败 MUST 记失败标记与原因，异常 MUST NOT 被吞掉。
- **FR-007**: 一次消息处理的编排 MUST 在入口处让"当前是哪个 Agent"对本次执行线程可见、在出口处（含异常路径）清除，MUST NOT 泄漏给复用同一线程的下一条请求。
- **FR-008**: 一次处理结束后 MUST 持久化会话状态。
- **FR-009**: 启动上下文（启动信息文件与绑定的能力包元数据）MUST 每次组装时重新读取、MUST NOT 缓存；被显式引用的文件缺失 MUST 报错，启动信息文件缺失 MUST 至少告警。能力包元数据本节按"名单 → 公共能力包库"直取，MUST NOT 预载其正文/附属资源。
- **FR-010**: 三种触发源（终端、HTTP、定时）MUST 复用同一个处理入口，不得各自实现循环。
- **FR-011**: 循环的调度职责 MUST 只包含"转圈、判断是否结束、累积结果"；拼上下文、请求模型、执行工具 MUST 分别由独立部件承担，循环内 MUST NOT 出现模型调用或工具执行的旁路。

### Key Entities *(include if feature involves data)*

- **会话状态**：一次对话的全部状态——身份（会话、所属 Agent、接入渠道、用户）与按序累积的对话消息（用户消息、每轮模型响应、每次工具执行结果）。本模块内为内存态，持久化的完整实现归后续节。
- **每轮上下文**：发给模型的四部分拼装结果（角色与启动信息、长期记忆、对话历史、工具说明），不是持久化数据，是每轮现拼的请求内容。
- **启动上下文**：来自工作区的文本——启动信息文件内容与绑定的能力包元数据（名称、描述、本地读取路径），每次组装现读。
- **工具调用审计记录**：一次工具执行的留痕——会话、工具名、调用参数、执行结果、成败、失败原因、耗时、时间。
- **当前 Agent 标识**：一次处理期间对执行线程可见的 Agent 配置引用，处理结束即清除。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 模型持续要求调用工具的用例中，模型调用次数恰好等于配置的最大轮数（0 次多余调用），返回值 100% 含"达到最大轮数"语义的收尾信号。
- **SC-002**: 成功与失败两类工具执行各留 1 条审计记录，失败记录 100% 带原因；抽查任一记录均含会话、工具名、耗时。
- **SC-003**: 对话历史超过上限时，注入的历史轮数 ≤ 上限（断言精确值，不是"大概被截断"）。
- **SC-004**: 处理过程抛异常的场景中，"当前 Agent 标识"100% 被清除（0 次泄漏）；正常处理结束后同样为 0 次残留。
- **SC-005**: 启动信息文件修改后，下一次组装上下文 100% 读到新内容（0 次读到旧内容）。
- **SC-006**: 可自动化验收全部由课件"验收 harness"的五个测试套件承载（循环调度、上下文组装、工具执行、处理编排、启动上下文加载），套件全绿即实现完成；剩余人工项见课件"做完怎么验"（真模型跑通 Demo 一对话版、code review 确认循环为自实现而非框架封装）。

## Assumptions

- 命名口径：课件示例的 OryxOS 命名统一映射到仓库 fourfeetcat 命名（工作区目录为 `.fourfeetcat/`，模块与包以 `fourfeetcat-*` 表达）。
- 依赖第16节交付的 Provider 能力：循环每轮经它请求一次模型；LLM 调用的审计口径与第16节保持一致，本节不重复实现。
- **前向契约（经主公裁决）**：会话状态的持久化出口、工具"从表里按名找到并执行"的能力、长期记忆供给，分别归属后续节（第18、20、22 节）。本节按最小前向契约接线：会话状态与持久化出口在核心层立最小形态；工具执行经本节自造的最小执行端口接入，第20节立统一工具抽象时合并、替换该端口；长期记忆以中性供给函数注入（缺省空实现=未启用），第22节传方法引用即可，组装器签名不变。
- 启动信息文件清单、能力包绑定清单均取自 Profile 已建全的字段；本节只是消费，不改 Profile 契约。能力包元数据按名单直取公共能力包库（第29节换成 Agent 目录相对软连接视图，对外行为不变）。
- 范围边界（课件"有几样先别做"）：工具并行调用、Agent 之间互相委托、流式输出、上下文压缩——不做；历史只用"只留最近 N 轮"顶着，压缩留扩展阶段。
