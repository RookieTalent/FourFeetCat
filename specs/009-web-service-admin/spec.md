- Q: 管理台的「会话列表」页要调 `GET /api/v1/sessions`，但课件「本节交付物」与 `docs/TechnicalSolution.md` §7.2 都把核心阶段钉死为"10 个端点"，会话组 4 个里没有列表端点——加端点还是改页面？ → A: **加第 11 个端点**。补一个只读的会话列表端点，复用既有的"按最后活跃时间倒序列举"仓储方法（与 `session list` 命令同源）。管理台按课件提示词原样落地，不做页面缩水。代价是"核心阶段 10 个端点"这一表述在 `CLAUDE.md` 与 `docs/TechnicalSolution.md`（3 处）需同步改为 11 个。
- Q: 运行信息端点里的"各 Provider 连通状态"按哪种口径实现——真发一次网络探测，还是只报配置态？ → A: **配置态，不联网**。逐 Provider 返回名字、端点与"凭证是否已就位"，不发探活请求。理由：该端点的冒烟验证 MUST 不依赖模型（课件"验收 harness"要求），真探测会让冒烟测试变成网络依赖；且本仓"零 key 可 boot"是既有口径，真探测在零 key 部署下必然全红，把"没配 key"与"服务不可达"两件事混成一种现象。
- Q: 管理台前端工程怎么串进构建？课件要求 plan 二选一（构建插件绑进 Maven / 手动构建）。 → A: **绑进 Maven 构建**。前端的依赖安装与构建绑进 Maven 构建生命周期，一条构建命令即产出含管理台的完整产物，"全量构建门禁全绿"因此同时覆盖后端与前端。代价是首次构建需联网拉取前端工具链与依赖。
- Q: 一次性调用（无状态 invoke）的会话怎么落？（若同一 Agent 的所有一次性调用共用一条会话，历次无关调用会互相污染上下文；若每次独立，每次都会多落一条会话行。） → A: **每次独立**。每次调用使用带唯一值的会话身份，会话标识仍由会话管理器按既有三元组规则生成（MUST NOT 自行拼接）；换来的是"无状态"语义名副其实——上一次调用的历史不会被回放给下一次。代价：每次调用落一条会话行，管理台的会话列表会出现大量一次性记录（如实呈现，不做隐藏）。
- Q: 「归档会话」对后续查询与发送有什么约束？ → A: **软标记 + 拒发**。归档只置状态与归档时间，数据一行不删；列表端点照常列出并带状态；按标识查历史仍可查到；向已归档会话发消息 MUST 明确拒绝（参数错误），MUST NOT 静默复活成活跃会话。列表不做归档过滤——"列表 = 全部会话"保持为真，归档与否由状态字段表达。
- Q: 「Agent 调用最长 60 秒 → 504」这条怎么落地？ → A: **卡在单次模型调用边界**。在模型调用的客户端构造处设 60 秒读超时，超时上抛专用异常并映射为 504——真超时、真 504，且仍留在同步阻塞模型内（不起额外线程、不引入异步）。已知局限：一轮多轮工具循环的总时长不受此上限约束，受约束的是单次模型调用；整轮墙钟上限留给后续阶段。
- Q: 管理台的设计 token 以哪边为准？（课件"页面风格"章给的是深色底 `#000000` + 主色橙 `#f97316` + 字体 Inter，并声称"值取自官网首页、与首页完全一致"；但本仓官网首页当前实际口径是明亮白底 `#FFFFFF` + 猫蓝主色 `#3D6FD6` + 中文优先字体族，橙色在首页里根本没出现，课件点名的样式文件在本仓也不存在——那份色值描述的是旧版官网。） → A: **以官网实际为准**。逐项取官网首页当前样式定义的真值，课件的深色 + 橙色值登记为过期（不采用）。理由：课件该章的核心意图是"钉死到官网首页的设计语言，一个字别自创"，目标是同源；照过期值做恰恰会造出与首页不同源的界面，并与本仓"README / 官网 / 文档 三处同一事实"的铁律相悖。取舍点：放弃课件字面色值，保住同源这条真意图。
- Q: 课件"决策四"要求把某个会急切实例化模型组件、索要第二份凭证的自动装配类排掉——但这行排除项还加不加？（本地核实：锁定版本 `spring-ai 1.1.2` 的模型核心件内**不含任何自动装配条目**，依赖树里也没有对应的自动装配件；本仓的模型组件从一开始就是显式构造的，那个"启动即索要第二份凭证"的坑本仓不存在。旁证：现有配置已在排除一个同样不在类路径上的自动装配类，而上下文启动正常。） → A: **不加，用测试守**。不写指向不存在类的死配置（会误导后人以为该自动装配件在类路径上）；把真实需求——零凭证下服务能起来、且运行信息端点如实报告凭证未就位——写成断言守住。课件那条决策的**意图**（不因框架急切装配而索要第二份凭证）由该断言承载，形式按本仓现状落地。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 业务系统用 HTTP 把 Agent 接进自己的流程 (Priority: P1)

业务系统（工单系统、运维平台、客服后台）需要在自己的流程里调 Agent：要么先建一条会话、多次发消息保持上下文，要么直接对某个 Agent 发起一次性调用、拿到结果就走。两种用法都只依赖 HTTP 与 JSON，不需要部署 Java 客户端、不需要知道底座内部怎么组织。

**Why this priority**: 这是本节的全部价值——在此之前的四大能力只有命令行一个出口，业务系统根本接不进去。没有这一层，"底座"就只是一个 CLI 工具。

**Independent Test**: 起服务后只用 HTTP 客户端走一遍：建会话 → 发消息拿到回复 → 查历史看到这轮对话 → 归档；再走一遍一次性调用路径拿到回复。全过程不看服务端日志、不用命令行。

**Acceptance Scenarios**:

1. **Given** 服务已启动，**When** 客户端请求创建一条会话，**Then** 返回该会话标识，后续请求可凭它继续。
2. **Given** 一条已存在的会话，**When** 客户端发送一条消息，**Then** 在响应里拿到 Agent 的回复，且这条消息与回复都能在随后的查历史请求中读到。
3. **Given** 一条已存在的会话，**When** 客户端请求归档，**Then** 该会话被标记归档，不再作为活跃会话出现。
4. **Given** 一个已加载的 Agent，**When** 客户端对它发起一次性调用，**Then** 在响应里拿到回复；响应 MUST NOT 要求客户端提供或持有会话标识。
5. **Given** 客户端请求会话列表，**When** 请求返回，**Then** 得到全部会话（最近活跃的在前），每项含标识、渠道、用户、所属 Agent、状态与时间。

### User Story 2 - 一次请求出错，客户端拿到的是可预期的统一格式 (Priority: P1)

客户端发来的消息超长、会话不存在、模型侧故障、处理超时：无论哪种，回来的都是同一个 JSON 信封——状态码符合 HTTP 语义、带一个可读的错误消息与时间戳。客户端不需要逐个端点猜错误格式，也不需要为每种错误写一套解析。

**Why this priority**: 对外的门面，错误格式的一致性就是契约本身。业务系统对接时最先踩的坑就是"同一个底座每个端点错误格式都不一样"。

**Independent Test**: 对每个端点各构造一次失败（超长消息、不存在的会话标识、内部异常），断言状态码与信封字段一致；再断言内部异常的细节一个字都不出现在响应体里。

**Acceptance Scenarios**:

1. **Given** 一条超过长度上限的消息，**When** 客户端发送，**Then** 返回参数错误状态码，响应体是统一信封。
2. **Given** 一个不存在的会话标识，**When** 客户端请求它的历史或向它发消息，**Then** 返回资源不存在状态码，响应体是统一信封。
3. **Given** 处理过程中抛出内部异常（例如数据访问故障），**When** 请求返回，**Then** 返回内部错误状态码，响应体是统一信封，且响应体与响应头里 MUST NOT 出现内部异常的消息、堆栈、连接串或表名。
4. **Given** 模型服务不可用，**When** 请求返回，**Then** 返回服务不可用状态码；**Given** 一次处理超过时长上限，**When** 请求返回，**Then** 返回超时状态码。
5. **Given** 任一端点的任一次成功响应，**When** 客户端解析，**Then** 得到与错误响应同构的信封（同一组字段）。

### User Story 3 - 运营方一屏看清底座里有什么、健康不健康 (Priority: P2)

运营方在浏览器里打开管理台，不需要命令行、不需要数据库客户端，就能看到：有哪些会话、加载了哪些 Agent、注册了哪些工具、长期记忆里记了什么、各 Provider 的凭证是否就位。这一版只能看，不能改。

**Why this priority**: 它是本节"API 是完备的对外通道"这一判断的验证——管理台自己没有后端，五个页面全部只调已发布的查询端点。排在 P1 之后是因为它不新增对外能力，只消费 P1 交付的端点。

**Independent Test**: 起服务后打开管理台首页，逐个切换五个页面，断言每页都渲染出真实数据（不是占位），且页面上不存在任何新建/编辑/删除入口。

**Acceptance Scenarios**:

1. **Given** 服务已启动且已有若干会话，**When** 打开管理台的会话页，**Then** 列出这些会话及其状态与时间。
2. **Given** 已加载若干 Agent、注册若干工具，**When** 分别打开对应页面，**Then** 列出每个 Agent 的可读配置（展示名、描述、provider/模型、可用工具）与每个工具的名称、描述、参数说明。
3. **Given** 长期记忆非空，**When** 打开记忆页，**Then** 展示长期记忆全文；为空时展示明确的空态占位而不是空白页。
4. **Given** 任一页面正在加载或请求失败，**When** 用户查看，**Then** 分别看到加载态与错误态（错误态展示统一信封里的可读消息），不出现白屏。
5. **Given** 管理台的任一个页面，**When** 逐一审视界面元素，**Then** 不存在新建、编辑、删除、启动、停止等写操作入口。
6. **Given** 用户停留在管理台的某个子路径并刷新浏览器，**When** 页面重新加载，**Then** 正常渲染该页面而不是资源不存在。

### Edge Cases

- **消息内容为空或只有空白**：按参数错误处理，不发起一次注定白烧的模型调用。
- **消息长度恰好等于上限**：放行；仅超过上限拒绝（边界值不因"防呆"被误伤）。
- **会话历史超过返回上限**：只返回最近若干条，并让客户端能看出这是被截断后的结果（不静默给出不完整历史）。
- **归档一条已经归档的会话**：幂等成功，不报错（归档时间保持首次归档那一刻，不被覆盖）。
- **向已归档的会话发消息**：返回参数错误并给出可读原因，不静默复活成活跃会话；要接着聊就新建一条会话。
- **一次性调用一个未加载的 Agent 名**：返回资源不存在，NOT 内部错误——名字写错是客户端的问题。
- **高并发的一次性调用**：每次独立建会话，会话行随调用数增长——如实落库（审计优先），本节的会话列表不分页，规模由使用方自负。
- **服务端完全没有配置任何 Provider 凭证**：服务 MUST 能正常启动，运行信息端点如实报告"凭证未就位"，不得因缺凭证启动失败。
- **管理台页面在数据为空时**：三个列表页与文本页都要有明确空态，不出白屏、不出误导性的"0 条"表格骨架。
- **管理台请求失败（服务不可达 / 端点报错）**：页面上展示可读错误消息，不静默吞掉、不显示与页面无关的报错。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供统一前缀的 REST 端点，按资源分成六个职责域：会话管理、Agent 调用、Agent 配置查询、记忆查询、工具信息、系统状态。前缀与路径口径 MUST 与既定设计一致，MUST NOT 另起前缀。
- **FR-002**: 会话管理 MUST 提供五项能力：创建会话、向指定会话发消息、按标识查会话历史、归档会话、只读列举会话（列表为本节新增的第 11 个端点，用于管理台与业务系统；列举按最后活跃时间倒序、含全部会话不分归档与否、与既有命令行查询同源）。
- **FR-003**: 发消息端点 MUST 复用与人推完全相同的处理入口（命令行 `chat` 走的就是它）；响应 MUST 含 Agent 的回复文本；目标会话已归档时 MUST 返回参数错误，MUST NOT 静默复活它。
- **FR-004**: 查历史端点 MUST 返回该会话的消息列表（归档会话同样可查），且在超过返回上限时只返回最近若干条（见 FR-011 的上限值）。
- **FR-005**: 一次性调用端点 MUST 对指定名字的 Agent 发起一次完整处理并返回回复；客户端 MUST NOT 被要求维护会话标识。每次调用 MUST 使用独立的会话身份（会话标识仍由既有唯一位置按三元组生成，端点 MUST NOT 自行拼接），MUST NOT 与既往调用或彼此复用同一条会话。
- **FR-006**: Agent 配置查询端点 MUST 列出全部已加载 Agent 的可读字段（展示名、描述、provider 与模型、可用工具、可用渠道）；MUST NOT 返回凭证类字段。
- **FR-007**: 工具信息端点 MUST 列出全部已注册工具的名称、描述与参数说明。
- **FR-008**: 记忆查询端点 MUST 返回长期记忆全文；为空时 MUST 返回可辨识的空内容而不是错误。
- **FR-009**: 系统状态 MUST 提供健康探针与运行信息两个端点；运行信息 MUST 含各 Provider 的名字、端点与"凭证是否已就位"，MUST NOT 发起真网络探测。
- **FR-010**: 每个端点 MUST 遵守"只做参数校验、响应包装、错误处理"——实际逻辑一律委托给核心层；MUST NOT 在端点实现里夹带业务逻辑（可测：一次正常请求恰好触发一次核心处理入口调用）。
- **FR-011**: 系统 MUST 对输入做防呆：单条消息最大 32KB（超过即参数错误）；会话历史返回最多最近 100 条。
- **FR-012**: 所有异常 MUST 由唯一一处全局异常处理器转成统一 JSON 信封（状态码 + 消息 + 时间戳，成功与失败同一组字段）。状态码口径 MUST 为：参数错误 400、资源不存在 404、内部错误 500、Provider 故障 503、处理超时 504。端点实现 MUST NOT 自行拼装错误响应。超时口径 MUST 落在单次模型调用边界（客户端读超时 60 秒，传输层超时由该唯一出口识别并映射为 504），MUST NOT 为此引入额外线程或异步模型；已归档会话的拒绝走参数错误。
- **FR-013**: 内部错误（500）的响应体与日志 MUST 分离：内部细节（异常消息、堆栈、连接串、表名）只进日志，对外 MUST 只给统一话术。
- **FR-014**: 每个请求 MUST 跑在独立虚拟线程上；实现 MUST 保持同步阻塞模型，MUST NOT 引入响应式编程模型。
- **FR-015**: 服务 MUST 在只配置一份 Provider 凭证（甚至零凭证）的情况下正常启动，MUST NOT 因框架预先实例化某个用不到的模型组件而索要第二份额外凭证或启动失败。该行为 MUST 由测试断言守住（零凭证下起上下文 + 运行信息端点如实报告凭证未就位）；MUST NOT 靠写一行指向不存在类的排除配置来"实现"（见 Clarifications）。
- **FR-016**: 系统 MUST 自动生成并暴露可访问的 OpenAPI 接口文档，MUST NOT 手写接口文档文件。
- **FR-017**: 系统 MUST 在 `/admin` 子路径下托管一个只读的单页管理台，含五项导航：会话列表、Agent 列表、工具列表、长期记忆、运行状态。
- **FR-018**: 管理台 MUST 只读：MUST NOT 出现任何新建、编辑、删除或启停入口（唯一的只读口径见本 FR，其余章节不得另立口径）；MUST NOT 调用**本节已发布的只读 GET 端点**之外的任何端点——即会话列表、会话详情、Agent 列表、工具列表、长期记忆全文、运行信息这六个 GET 之外的一律不调（含所有写方法）。
- **FR-019**: 管理台 MUST 具备加载中、空数据、请求失败三种明确占位状态；失败时 MUST 展示统一信封里的可读消息。
- **FR-020**: 管理台的前端子路径 MUST 支持直接访问与刷新（未命中的前端路由回落到管理台入口页），且 MUST NOT 影响 API 前缀下的行为。
- **FR-021**: 管理台的视觉 MUST 沿用官网首页的设计语言——取值 MUST 逐项取自官网首页**当前实际**的样式定义（本仓官网现为明亮白底 + 猫蓝主色 + 中文优先字体族，等宽字体用于代码/标识/JSON），MUST NOT 自创一套视觉，也 MUST NOT 沿用任何过期色值；这套设计约定与工程约定 MUST 固化为一份项目内可复用的说明文件，供后续节给管理台加页面时复用。
- **FR-022**: 管理台的前端源码与其构建产物 MUST 落在既定的模块内（源码随 Web 模块、产物由服务直接托管），MUST NOT 另建模块或引入独立后端。

### Key Entities *(include if feature involves data)*

- **会话（对外视图）**：标识、渠道、用户、所属 Agent、状态、创建时间、最后活跃时间——即列表端点与查历史端点对外呈现的形状。状态取值区分活跃与已归档；归档不删数据。
- **一次性调用会话**：由无状态调用端点每次新建的会话，身份含唯一值、彼此不共用；它与对话会话同表同结构，区别只在身份与生命周期（一次性会话不会被后续调用复用）。
- **Agent 配置（对外视图）**：展示名、描述、provider 与模型、可用工具、可用渠道、可用记忆后端等可读字段；凭证类字段一律不出现。
- **工具描述（对外视图）**：名称、描述、参数 JSON Schema。
- **统一响应信封**：成功与失败共用的同一组字段——状态码、消息、数据体、时间戳。
- **Provider 状态（对外视图）**：名字、端点、凭证是否已就位（不含凭证本身）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 只用 HTTP 客户端即可完成"建会话 → 发消息 → 查历史 → 归档"与"一次性调用"两条主路径，全程零命令行、零数据库操作。
- **SC-002**: 端点数为 11（原 10 个 + 会话列表 1 个）；六个职责域各至少一个端点，验收时逐条 curl 可达。
- **SC-003**: 错误格式统一率 100%：失败响应的字段结构与成功响应完全一致；内部错误的响应体里内部细节出现次数为 0（对连接串、表名、异常消息各断言一次）。
- **SC-004**: 端点薄度可测：一次正常发消息请求下核心处理入口被调用次数恰为 1（多一次即"端点夹带私货"，0 次即"没接到同一个人推入口"）。
- **SC-005**: 冒烟可达：不依赖模型、不依赖外部网络的前提下，健康探针、运行信息、Agent 列表、工具列表四个端点真实链路可达（证明组件装配与数据访问层扫描范围无误）。
- **SC-006**: 零凭证可启动：不设任何 Provider 凭证环境变量的干净环境下，服务启动成功且运行信息端点如实报告"凭证未就位"。
- **SC-007**: 管理台五页全部渲染真实数据、无任何写操作入口；三态（加载/空/错误）齐备；子路径刷新不出现资源不存在。
- **SC-008**: 一次全量构建即产出含管理台的完整产物（无需先手工构建前端），且全量构建门禁（含静态检查与安全检查）全绿。
- **SC-009**: 前序各节的测试零断言删改、零用例跳过；本节交付时全量测试全绿。
- **SC-010**: 管理台视觉与官网首页同源：颜色与字体取值逐项取自官网首页**当前实际**的样式定义（逐项可对号，无自创值），且该组取值与工程约定可在项目内说明文件中查到（后续节加页面直接复用，不重新发明）。
- **SC-011**: 无状态名副其实：连续两次一次性调用拿到两条不同的会话标识（断言不相等），且第二次调用的上下文里不含第一次的内容。
- **SC-012**: 归档硬边界：归档后按标识仍可查到该会话（状态为已归档），向它发消息得到参数错误且其状态未被改回活跃；重复归档幂等。

## Assumptions

- **内网部署、无认证**：本节不做认证、鉴权、限流、跨域白名单——假设服务只对内网开放（这些是扩展阶段的清单）。因此"谁能调这些端点"不在本节的成功标准内。
- **不做流式**：响应一律一次性返回；流式与长连接不在本节范围。
- **不做写操作**：管理台与 API 都不提供 Agent 配置的增删改（那需要"通过 API 定义一个 Agent"的完整链路，属后续节）；本节的运行信息里"凭证是否就位"只读、不可在界面上修改。
- **超时口径**：60 秒上限落在单次模型调用（客户端读超时），超过即返回超时状态码；一轮多轮工具循环的总时长不受此上限约束（见 Clarifications）；不做重试与后台续跑。
- **并发口径**：并发能力由虚拟线程与既有的单写者数据源配置共同决定；本节不做压测门槛，只保证不引入阻塞整个服务的全局锁。
- **前端工具链**：构建机需具备联网能力以获取前端工具链与依赖（本地已验证具备 Node/npm 环境）；管理台的构建产物由服务直接托管，不入库、不参与后端静态检查。
- **依赖前序节交付**：Provider 显式映射与调用入口、ReAct 循环与统一处理入口、会话管理器与会话仓储、Agent 配置注册表、工具注册表、记忆门面、沙箱白名单——以上均已就位，本节只做对外包装，不改动它们的既有契约。
- **文档同步**：因新增第 11 个端点，`CLAUDE.md` 与 `docs/TechnicalSolution.md` 中"核心阶段 10 个端点"的表述需同步修订（共 4 处），这是本裁决的既定代价。
