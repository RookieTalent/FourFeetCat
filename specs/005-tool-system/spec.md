## User Scenarios & Testing *(mandatory)*

### User Story 1 - 三种来源的工具收敛成一个样子，执行循环对来源无感知 (Priority: P1)

底座自带的工具、业务方用 Java 写的工具、通过外部服务接进来的工具，来源五花八门。执行循环如果按来源区别对待，代码会很快乱掉。所以先把它们全部包装成同一个样子注册进一张表，循环只跟这张表打交道。Agent 启动时再按自己声明的"我能用哪些工具"从表里取一个子集——不多给也不少给。

**Why this priority**: 这是整个 Tool 体系的地基，后面所有工具（内置的、业务方接的、后续节要加的）都往这个形状里塞。抽象一旦歪了，工具越多越难改。它也是"加一个新工具的成本恒定在写一个类"这句话成立的前提。

**Independent Test**: 往表里注册几个来自不同来源的工具替身，断言按名取到的描述、按名执行的结果都对；再按一份声明清单取子集，断言子集恰好等于清单。

**Acceptance Scenarios**:

1. **Given** 若干来自不同来源的工具，**When** 它们被注册进工具表，**Then** 取出来的每一个都具备"名字 + 用途描述 + 参数说明"三件套，且调用方无需知道它原本来自哪里。
2. **Given** 一个 Agent 声明了三个工具名，**When** 从表里过滤出它可用的工具，**Then** 得到的子集恰好是这三个（多一个、少一个都是错）。
3. **Given** 表里已有若干工具，**When** 遍历全表做契约检查，**Then** 任一工具的用途描述或参数说明为空都会立刻失败——漏了参数说明，把工具翻译成模型可读格式那一步会直接卡死。
4. **Given** 运行中的底座，**When** 查看当前注册了哪些工具，**Then** 得到一份可读清单。

---

### User Story 2 - 内置工具真的能动手，且踩不出边界 (Priority: P1)

Agent 要能读文件、写文件、列目录；要能跑白名单内的命令；要能发 HTTP 请求。每一样在真正动手之前，都得先过一道安全校验——校验不过，动作根本不发生。

**Why this priority**: 这是"Agent 能干事"的落点，也是安全底线。没有它，前面几节的 Agent 只是个会聊天的壳；没有校验，它就是个能被乱调的破坏源。

**Independent Test**: 对每一类内置工具跑两条——正常输入能拿到结果；越界输入（白名单外的路径 / 命令 / 域名）在动手前被拦下。

**Acceptance Scenarios**:

1. **Given** 一个白名单内的路径，**When** 读 / 写 / 列目录，**Then** 正常返回内容。
2. **Given** 白名单外的可执行命令、**或**白名单外的域名、**或**白名单外的文件路径，**When** 调用对应工具，**Then** 校验失败、动作不发生、调用方收到明确失败结果。
3. **Given** 一条执行超时的命令，**When** 执行它，**Then** 在限定时间内终止并返回失败，不无限挂住循环。
4. **Given** 命令输出了大量内容，**When** 返回结果，**Then** 超出上限的部分被截断并明确注明——一次全吐出去会把模型的上下文撑爆。

---

### User Story 3 - 业务方按三档接入自己的工具，门槛从低到高 (Priority: P1)

不同的人扩展能力的水平不一样：有人只想描述"我要干什么"、复用现成的外部工具服务，一行代码不写；有人愿意用任何语言写一个连接自家系统的外部工具服务；有人要用带注解的 Java 方法做进程内深度集成。三条路都要能走通，且走通之后 Agent 侧看不出差别。外部服务失联时，不能把底座自己的启动拖下水。

**Why this priority**: 企业场景下真正的业务能力都靠业务方接进来，底座自己只给基础工具。这一条决定了底座的扩展性是不是真的可用。

**Independent Test**: 用替身模拟外部工具服务，断言它暴露的工具被包装注册、调用参数原样转发、结果被包装成统一的结果值对象；再让其中一个服务连不上，断言其余工具照常注册、启动不抛异常。

**Acceptance Scenarios**:

1. **Given** 一份外部工具服务的声明（名字 / 传输方式 / 命令 / 环境变量），**When** 底座启动，**Then** 该服务暴露的工具出现在工具表里，Agent 能像调用内置工具一样调用它们。
2. **Given** 一个外部工具被调用，**When** 执行，**Then** 参数原样转发给它，返回结果被包装成统一的成功 / 失败结果。
3. **Given** 声明了多个外部工具服务，其中**一个连不上或取工具清单失败**，**When** 底座启动，**Then** 只有它的工具缺席（并在日志中留警告），其余服务照常注册，启动过程不抛异常。
4. **Given** 一个带注解的 Java 方法写成的工具放进工程，**When** 底座启动，**Then** 它被自动扫描、生成参数说明、注册进工具表。
5. **Given** 业务方只想描述意图、复用现成服务，**When** 他写一份说明并声明引用该服务，**Then** 不需要写任何代码就能让 Agent 用上这套能力（本项依赖后续节的 Agent 目录与 Skill 绑定，本节保证工具入口可用）。

---

### User Story 4 - 已有能力归位：推送成为可被调用的内置工具，记忆留好注册位 (Priority: P2)

第19节做好的"往外推通知"，要以内置工具的身份注册进来，Agent 在对话里就能说"把这条推到群里"。记忆模块的"记事 / 检索"同理——它的实现归第22节，但注册位必须在本节留好并验证过，否则 22 节交付时还得回头改注册管道。

**Why this priority**: 通知能力已经造好了，但第19节明说它的接线要等工具注册机制就位——本节正是那个时点。不接上，它就是一段没有出口的代码。

**Independent Test**: 用替身（校验组件与渠道适配器）跑通知工具——没配渠道时报错、渠道名缺省时取第一个、安全校验先于发送被调用；再用一档替身工具走通注册管道四步。

**Acceptance Scenarios**:

1. **Given** 一个已配置的通知渠道，**When** 让 Agent 推一条内容，**Then** 内容到达该渠道。
2. **Given** 一个渠道都没配置，**When** 调用通知，**Then** 得到明确报错，而不是静默成功。
3. **Given** 调用通知时不给渠道名，**When** 执行，**Then** 使用第一个已配置渠道。
4. **Given** 一次通知调用，**When** 观察调用顺序，**Then** 安全校验先发生、发送后发生（顺序反了就是绕过白名单的漏洞）。
5. **Given** 记忆工具（记事 / 检索）尚在第22节交付，**When** 本节验证"已有能力归位"这条链路，**Then** 用一档替身工具走通"注册 → 按声明清单过滤 → 执行 → 审计"四步，证明记忆工具就位时无需改动注册管道。

---

### Edge Cases

- 工具表里没有该名字：明确报错并指出名字，不静默少给——Agent 声明的工具不存在是配置错误。
- 参数说明为空的工具被注册：契约遍历检查立刻失败，不允许"先注册上以后再补"。
- 同一名字的工具被注册两次：后者覆盖或明确拒绝，必须有一个确定行为（不能随机取到一个）。
- 外部工具服务返回的失败：标记为"可重试"的失败回填给模型换招，不炸掉整轮。
- 命令输出过大：截断并注明，不把模型上下文撑爆。
- 命令执行超时：限时终止并返回失败，不让同步循环无限挂住。
- 外部工具服务在启动时连不上：只记警告、跳过它的工具，不阻断启动。
- 安全校验规则的正式实现尚未就位时：交付的是接口 + 一档不做校验的临时装配，其被替换的时点必须可被验证到，且必须显式标注。
- Agent 声明了一个尚未交付的工具名（如记忆工具，实现归第22节）：按名解析失败即明确报错并指出名字，不让 Agent 带着一个"其实用不了"的工具跑。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供统一的工具抽象，任何来源的工具（底座自带、业务方注解实现、外部服务接入）都被包装成同一形状：名字、用途描述、参数说明、执行。
- **FR-002**: 统一抽象 MUST 包含"参数说明"这一项；缺了它，把工具翻译成模型可读格式的一步将无处取值。系统 MUST 提供自动化守卫：遍历全部已注册工具，断言名字、用途描述、参数说明三者都非空，新增工具自动纳入检查。
- **FR-003**: 系统 MUST 提供统一的结果值对象：成功标识、结果内容、错误信息、是否可重试。失败结果 MUST 被回填进对话供模型换招，MUST NOT 以抛异常的方式炸掉整轮。
- **FR-004**: 系统 MUST 提供工具注册表，汇总三种来源的工具；Agent 启动时按自身声明的工具名清单过滤出可用子集，该子集 MUST 精确等于声明清单（多一个与少一个都视为错误）。
- **FR-005**: 系统 MUST 能列出当前注册了哪些工具（内省）。
- **FR-006**: 系统 MUST 提供内置文件工具三件：读文件、写文件、列目录。**本节 MUST NOT 交付**课件的扩展文件工具（按唯一文本替换、按内容搜索、按通配找路径）——它们登记为后续补充。
- **FR-007**: 系统 MUST 提供内置命令执行工具：按白名单精确放行可执行文件，参数以数组直传、MUST NOT 解释 shell 语法，并 MUST 有执行超时；输出 MUST 有长度上限，超出即截断并注明。（原稿的"条数上限"指的是按内容搜索类工具的命中条数，随该工具一并登记为后续补充。）
- **FR-008**: 系统 MUST 提供内置 HTTP 工具（GET 与 POST），受域名白名单约束。
- **FR-009**: 系统 MUST 提供内置记忆工具（记事 / 检索）的**注册位**：其实现归记忆模块，以工具身份注册。**本节 MUST NOT 实现记忆工具本体**——记忆模块在本节时点为空模块，抢跑会造出第二套记忆逻辑；本节 MUST 保证注册管道能容纳它：用替身工具验证"注册 → 按声明清单过滤 → 执行 → 审计"四步全通，记忆工具的任务 MUST 标注为跨节完成（完成时点在第22节）。
- **FR-010**: 系统 MUST 提供内置通知工具：把一条内容按渠道名推进全局注册表里登记的通知渠道；渠道名缺省时取第一个渠道；**一个渠道都没配置时 MUST 明确报错，MUST NOT 静默成功**。
- **FR-011**: 系统 MUST 支持接入外部工具服务：**启动时连接配置里声明的全部**服务（不按 Agent 逐个连），取其工具清单，把每个工具包装成统一抽象注册进注册表。配置形态为 名字 / 传输方式 / 命令 / 环境变量。Agent 侧的隔离 MUST 继续由"可用工具名清单"单一机制承担，MUST NOT 另起一层按 Agent 过滤外部服务来源。
- **FR-012**: 调用外部工具时，系统 MUST 原样转发参数，并把返回包装成统一结果值对象；失败 MUST 标记为可重试。
- **FR-013**: 任一外部工具服务连接失败或取清单失败时，系统 MUST 只记警告并跳过它的工具，MUST NOT 阻断自身启动或影响其余工具的注册。
- **FR-014**: 所有涉外工具（文件、命令、网络）MUST 在真正动手之前的第一步执行安全校验，校验不通过即拦下、动作 MUST NOT 发生。这是核心阶段唯一的工具治理手段。校验**规则的实现体**归后续沙箱节；本节 MUST 只交付抽象接口与一档不做实际校验的**临时装配**，MUST NOT 自造第二套校验机制，且该临时装配的替换时点 MUST 可被验证到、MUST 在交付物中显式标注。
- **FR-015**: 每次工具执行的成败 MUST 写入既有的调用留痕路径；本节 MUST NOT 新增审计逻辑或另建审计表。
- **FR-016**: 本节新增工具 MUST 复用同一套注册管道与同一个校验执行位——加一个新工具的成本 MUST 恒定在"写一个工具类"，不随工具数量增长而增加。
- **FR-017**: Agent 配置里声明的工具名清单语义 MUST 保持不变（第16节交付的字段类型与含义不改）。工具白名单与治理策略正交：MUST NOT 在本节引入"哪个 Agent 能用哪个工具"的 allow/deny 规则。
- **FR-018**: 课件第六部分的五个扩展工具（按唯一文本替换、按内容搜索、按通配找路径、中途问人、联网检索）MUST NOT 在本节实现；其任务 MUST 登记为跨节、本节不勾选。本节交付的注册管道 MUST 使它们后续落地时零改动即可挂入。

### Key Entities *(include if feature involves data)*

- **工具（统一形状）**：任何可被模型点名叫到的能力——名字（模型靠它点名）、用途描述（给模型看）、参数说明（参数长什么样）、执行入口。来源有三：底座自带、业务方注解实现、外部服务接入。
- **工具描述**：组装请求时递给模型的"有什么工具可用"那一份说明——名字 + 描述 + 参数说明。不是可执行体，是从注册表导出的一份视图。
- **执行结果**：一次工具执行的四样东西——成功标识、结果内容、错误信息、是否可重试。
- **外部工具服务声明**：一条接入配置——名字、传输方式、启动命令、环境变量。落配置文件，不落库。
- **安全校验动作**：一次待校验的涉外动作——动作类型（文件读 / 文件写 / 命令执行 / 网络请求）+ 目标（路径 / 命令 / 地址）。不是持久化数据，是执行前的入参。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 遍历工具表时，名字、用途描述、参数说明三项中为空者出现次数为 **0**；任一工具漏实现参数说明，遍历检查 100% 失败。
- **SC-002**: 按声明清单过滤的可测试用例中，子集与声明清单的差异条数为 **0**（多一个、少一个都判失败）。
- **SC-003**: 本节交付的每一类内置工具（文件、命令、HTTP、通知）都同时具备"正常能跑通"与"越界会被拦"两条自动化用例，覆盖率 **100%**。
- **SC-004**: 外部工具服务失联场景中，其余工具注册成功率 **100%**、启动中断次数 **0**。
- **SC-005**: 通知工具的顺序断言 100% 通过——安全校验必须先于发送发生，顺序反了即判失败。
- **SC-006**: 可自动化验收由课件"验收 harness"承载（`mvn test` 全绿即通过）：契约三件套遍历守卫、注册与按声明清单过滤、各内置工具的"正常 + 越界"两条、外部服务接入的包装与转发、外部服务失联隔离。另有按技术方案补的用例（通知工具的顺序断言与缺省行为、渠道按名解析）同节交付。
- **SC-007**: 安全校验临时装配的替换时点可被验证到——交付物中存在明确标注该装配为临时、且指明由后续沙箱节替换的记录。
- **SC-008**: 五个扩展工具的登记可见、且本节未实现——任务清单中它们存在且状态为未完成，代码中不存在对应实现类。

## Assumptions

- **命名（已裁决）**：统一工具抽象与结果值对象采用项目既定命名（与 `docs/TechnicalSolution.md` §6.1 及项目文档一致），不采用课件通用模板里的占位名；第17节已有类注释指向本节，其占位表述随本节一并订正。
- **渠道解析落点（已裁决）**：通知工具需要"按名解析通知渠道"。该解析能力不在课件本节交付物清单内，经裁决在 core 定端口、由 storage 读通知渠道表出实现、boot 装配——与第19节 research D8 约定的手法一致，依赖方向无环。
