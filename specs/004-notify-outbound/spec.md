## User Scenarios & Testing *(mandatory)*

### User Story 1 - 到点自动跑完的 Agent 能把结果主动送出去 (Priority: P1)

一个每天定时运行的日报类 Agent 到点自动跑完一轮，把汇总结果直接推进企业 IM 群。全程没有任何人在另一端等着接收响应——发起方是时钟，不是人。在此之前，Agent 跑出来的结果只能烂在会话历史里，谁也看不到。

**Why this priority**: 这是本模块存在的全部理由。没有出站通知，"到点自动"这类场景跑完等于白跑——结果没有出口。定时能力与两个 Demo（天气、日报）全靠它收口。

**Independent Test**: 起一个本地假接收端，向它推一条内容，断言内容真的到达；把接收端改成返错，断言错误被上抛而不是被吞掉。

**Acceptance Scenarios**:

1. **Given** 一个已配置好的通知渠道，**When** 把一条内容送到该渠道，**Then** 接收端收到一条携带该内容的请求，地址取自渠道配置而不是代码里写死的。
2. **Given** 接收端返回服务端错误，**When** 执行推送，**Then** 错误向上抛出，调用方不会以为"已经发出去了"。
3. **Given** 同一条内容要送到多个不同渠道，**When** 分别推送，**Then** 每条请求都送到各自配置的地址。

---

### User Story 2 - 换渠道不改 Agent、不改通知代码 (Priority: P1)

运营方要把日报从通用 webhook 换成某家 IM 的专用形态。这次改动**只动配置**：Agent 的定义、通知的调用点一行不改。未来新增一档渠道实现，接口签名也不需要变——用最重的那档实现去反向套这个签名，也应该能干净套入。

**Why this priority**: 这是"接口先行"这条设计习惯在项目里的第一次亮相，也是本模块留给扩展阶段的唯一扩展点。接口一旦带上某一档实现的词汇（渠道专有名词、认证字段），扩展阶段就只能改接口、连带改调用方。

**Independent Test**: 通读接口签名，确认其中不出现任何具体渠道名称或某一档实现特有的概念；把实现类替换成另一档的替身，调用方代码无需改动即可编译通过。

**Acceptance Scenarios**:

1. **Given** 出站通知的抽象接口，**When** 审阅其签名与参数类型，**Then** 签名里不出现任何具体渠道名或某一档实现特有的词。
2. **Given** 同一份调用方代码，**When** 把实现替换成另一档（如某家 IM 的专用实现），**Then** 调用方无需改动。
3. **Given** 通知目标的取值对象，**When** 检视其字段，**Then** 只有"渠道类型 + 一份配置"，具体含义由实现自己解释。

---

### User Story 3 - 渠道是全局配置，Agent 只按名引用 (Priority: P2)

运维方在实例级维护一份通知渠道清单（每个渠道一个全局唯一的名字），Agent 侧只声明"我可以用哪些渠道名"。通知地址不进对话上下文，也不写进 Agent 的配置正文——地址里的 token 本身就是凭证。

**Why this priority**: 渠道配置散落在每个 Agent 里会导致同一份地址重复维护、改一处漏一处；且地址含凭证，不该出现在会被模型看到的地方。

**Independent Test**: 在渠道表里存一条记录，能按名读回；Agent 配置里只出现渠道名，不出现地址。

**Acceptance Scenarios**:

1. **Given** 手工建表脚本建出的渠道表，**When** 写入一条渠道记录再按名读回，**Then** 各字段往返一致。
2. **Given** 一个 Agent 的配置，**When** 查看它声明的可用渠道，**Then** 里面只有渠道名，没有地址与凭证。
3. **Given** 两个 Agent 引用同一个渠道名，**When** 该渠道地址变更，**Then** 只需改一处（渠道表），两个 Agent 同时生效。

---

### User Story 4 - 在对话里直接让 Agent 推一条 (Priority: P3)

用户在对话里说"把这条测试消息推送一下"，Agent 调用通知能力，消息到达配置好的群。这条路径依赖"通知"作为内置工具被注册与执行——注册机制、工具结果类型与安全校验归后续节，**本节的完成时点在沙箱节之后**。

**Why this priority**: 它是本模块的"可对话验证"入口，但依赖后续节交付的接线能力，本节只能把契约与实现备好。

**Independent Test**: 用替身（校验组件与渠道适配器的替身）在本地跑通知工具：未配置渠道时报错、渠道名缺省时取第一个、安全校验先于发送被调用。

**Acceptance Scenarios**:

1. **Given** 一个没有配置任何通知渠道的 Agent，**When** 调用通知，**Then** 得到明确报错，而不是静默成功。
2. **Given** 一个配了渠道的 Agent，**When** 调用通知时不给渠道名，**Then** 使用第一个渠道。
3. **Given** 一次通知调用，**When** 观察调用顺序，**Then** 安全校验先发生、发送后发生（顺序反了就是绕过白名单的漏洞）。

---

### Edge Cases

- 渠道表里没有该名字：明确报错并指出名字，不静默失败。
- 渠道记录存在但地址字段为空：推送前就报错，不发一个空地址的请求。
- 同一渠道名重复写入：由主键唯一约束兜住，不产生两条同名渠道。
- 渠道地址含凭证：走环境变量占位解析，配置文件与库中不留明文（地址即凭证）。
- 接收端超时或不可达：与 5xx 同样上抛，不吞。
- 一次要推的内容超过接收端限制：本节不做分段（核心阶段克制），由调用方自行控制长度。
- 依赖后续节的接线尚未就位时：通知工具的相关任务不得被标记完成。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供出站通知的抽象契约，只表达"把一条内容送到某个通知目标"这一意图；签名与其参数类型 MUST NOT 出现任何具体渠道名或某一档实现特有的词。
- **FR-002**: 系统 MUST 提供"通知目标"取值对象，只承载渠道类型与一份配置；配置里是地址还是其他认证信息，由实现类自行解释。
- **FR-003**: 系统 MUST 提供核心阶段唯一一档通用 webhook 实现：从目标配置取地址，以 JSON 形式 POST 一条携带内容的请求；HTTP 客户端 MUST 经构造注入以便替换与测试。
- **FR-004**: 推送失败（接收端返回服务端错误、超时、不可达）MUST 让异常向上抛出，MUST NOT 被吞掉或降级为成功。
- **FR-005**: 通知渠道 MUST 采用全局注册表形态：每个渠道有全局唯一的名字，持久化落库；Agent 侧只声明可用渠道名，地址与凭证 MUST NOT 出现在对话上下文或 Agent 配置正文里。
- **FR-006**: 渠道表结构 MUST 由手工建表脚本管理（双轨、同版本号），MUST NOT 依赖持久化框架自动建表。
- **FR-007**: 渠道地址与凭证 MUST 走环境变量占位，明文 MUST NOT 写进配置文件、库表或日志。
- **FR-008**: 向外发送是一次对外 IO，MUST 在调用点预留安全校验的执行位并注明校验归后续沙箱节接线；本节 MUST NOT 自造第二套校验机制。
- **FR-009**: 通知作为内置工具的完整接线（工具注册、工具结果类型、安全校验）依赖后续节交付；本节 MUST NOT 以替代端口或临时形态抢跑该接线，其任务 MUST 标注为跨节完成。

### Key Entities *(include if feature involves data)*

- **通知目标**：一次推送的目的地描述——渠道类型 + 一份配置（具体含义由实现解释）。不是持久化数据，是调用时的入参。
- **通知渠道（注册表记录）**：全局唯一的渠道登记项——名字（唯一标识）、类型（决定由哪档实现处理）、地址（HTTP 类渠道）、描述（可空）、以及承载类型相关多字段的扩展配置。落库持久化，Agent 按名引用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 通用 webhook 实现发出的请求，body 中 100% 携带所传内容，且地址 100% 来自通知目标配置（改配置即改地址，0 处硬编码）。
- **SC-002**: 接收端返 5xx 的场景中，异常 100% 向上抛出（0 次静默吞掉）。
- **SC-003**: 渠道表经手工建表脚本建出后，写入再读回 100% 字段一致。
- **SC-004**: 接口签名中具体渠道名与实现特有词出现次数为 **0**（人工审阅，课件列为人工作业项）。
- **SC-005**: 可自动化验收由课件"验收 harness"承载——第一批（通用 webhook 实现）本节即可全绿；第二批（通知工具的顺序断言与缺省行为）的完成时点在沙箱节之后，本节只保证其任务已被登记且不被标记完成。另有按技术方案补的渠道表守点同节交付。
- **SC-006**: Agent 配置中出现的通知相关内容 100% 是渠道名，0 处地址或凭证。

## Assumptions

- **渠道形态（已裁决）**：采用全局注册表（技术方案 §6.8 与课程建表脚本口径），不做 Agent 配置内联结构化配置；第16节已交付的"可用渠道名清单"字段本节不改其类型与语义。
- **假接收端（已裁决）**：用 JDK 内置的 HTTP 服务类实现，不引入新增第三方测试依赖。
- **本节范围（已裁决）**：只交付契约 + 目标值对象 + 通用 webhook 实现 + 其测试 + 渠道表；通知工具的完整接线列为跨节任务。
- 核心阶段不提供渠道的写入入口（管理台与端点归扩展阶段），表数据靠手工或后续管理台填充——因此本节交付的表在核心阶段是"结构就位、写入待后续"。
- **审计口径**：通知推送作为内置工具被调用时，**走既有的工具执行审计路径**（成功失败都留痕），本节不新增任何审计逻辑、不另建审计表——与既有审计机制同款（技术方案 §6.8）。该行为随工具接线的落地时点一起生效。
- 依赖前序节交付物：Agent 配置值对象（渠道名清单字段）、持久化模式（实体 + 仓储 + 双轨迁移脚本 + 手工建表测试）、编排上下文（工具执行时能拿到"当前是哪个 Agent"）。
- 范围边界（课件"几样先别做"）：不逐家接渠道专用 API（签名算法、令牌刷新）、不做邮件短信等非 HTTP 渠道、不做渠道管理台与增删改查端点、不在本节完成内置工具接线。
