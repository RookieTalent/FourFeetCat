## Clarifications

### Session 2026-09-28

**开工前（三处课件/技术方案未定死的口径，经主公裁决）：**

- Q: 定时模块要消费的定时配置，是否改成强类型对象、由配置加载器负责解析与校验？（强类型会让坏 cron 连带整份 Agent 配置被跳过；保持原样则改动面最小。） → A: **保持原结构不变**。已交付的 Agent 配置里那个定时配置字段（原始条目列表）一行不动，其既有的加载器与既有测试夹具照旧；强类型对象由调度模块在注册时逐条解析，坏的一条例外、记错误日志、跳过，不牵连同一 Agent 的其他条目与整份配置。
- Q: 条目里那个任务标识从哪里来？（课件与技术方案均未给配置样例；后续阶段要把它当稳定键做状态协调，而现有测试夹具里的条目根本没写标识。） → A: **标识可选，缺省派生**。配置里可显式写标识；不写则按"Agent 名 + 条目序号"派生。手写配置最省事，需要稳定键时再显式写。同一 Agent 内标识重复视为配置错误：记错误日志、跳过后出现的那条并点名两条来源。
- Q: 定时注册在哪些运行模式下生效？（课件只说"启动时扫一遍"，技术方案 §8.6 说定时任务随常驻模式一起调度，未说交互模式必须不注册。） → A: **与运行模式无关**。引擎装配时即注册——常驻模式因此持续调度；交互式对话是短会话，进程退出即停。不为此新增配置开关（多一个"要不要调度"的开关，等于把"配置即 Agent"又拧回去一半）。
- Q: 触发规则采用哪种 cron 方言？（课件正文只写"cron 表达式"并给出 `0 9 * * *` 这类 5 段 Unix 写法，本仓既有测试夹具也沿用了它；而实测本地依赖里调度框架的 cron 触发器只收 6 段：`Cron expression must consist of 6 fields (found 5)`。） → A: **用框架原生 6 段**（秒 分 时 日 月 周），配置说明里写明格式，不做 5 段 → 6 段的兼容转换。理由有二：一是零转换代码，注册时交给调度器的表达式与配置原文逐字一致（这本身是一条可断言的成功标准）；二是 5 段写法会被**响亮拒绝**（实测为参数异常，不会被静默误读成"每小时第 9 分钟"），按 FR-010 记错误日志并跳过该条。代价是课件与既有夹具里的 5 段样例需在配置说明中改口径。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 到点 Agent 自己跑一轮，人不必在场 (Priority: P1)

业务方在 Agent 的配置里写下"每天 09:00 说这句：汇总昨天的 PR 评审进度"。进程常驻起来之后，每天到点由系统自己拼出这条消息、交给跟人推完全相同的处理入口跑完一轮；消息说什么由配置决定，跑完之后的循环、工具、模型调用与推送，定时这一层一概不管。

**Why this priority**: 这是本节的全部价值——补上基础能力的最后一个缺口"不用人喂话，自己到点干活"。没有它，后面的每日天气、每日科技日报两个验收场景都缺一条腿。触发那一刻是否走同一个人推入口，决定了这条能力是"引擎的一部分"还是"引擎旁边另搭的一套"。

**Independent Test**: 在一个 Agent 的配置里声明一条"每分钟"的定时任务，让它跑起来，断言：注册时交给调度器的触发规则与时区跟配置逐字一致；人为触发一次后处理入口被调到一次，且传入的消息就是配置里那句话；这条任务的历次触发落到同一个会话上。

**Acceptance Scenarios**:

1. **Given** 某 Agent 的配置里声明了一条带触发规则与消息内容的定时任务，**When** 进程启动完成，**Then** 这条任务已被注册进调度器，且注册时携带的触发规则与配置逐字一致。
2. **Given** 一条已注册的定时任务，**When** 触发点到（含手工触发一次以省去等待），**Then** Agent 的处理入口被调用一次，消息内容即配置里声明的那句话。
3. **Given** 同一条定时任务的两次先后触发，**When** 两次都取得会话，**Then** 两次拿到的是同一个会话——渠道与用户固定为定时专用身份、Agent 名取该任务所属 Agent，不为人推以外新设会话概念。
4. **Given** 一个 Agent 没有任何定时配置，**When** 进程启动，**Then** 不注册任何任务，其余能力零变化。
5. **Given** 配置里写了时区，**When** 该条被注册，**Then** 触发规则与该时区一并交给调度器（不让服务器时区替用户做主）；**When** 配置没写时区，**Then** 按服务器系统时区运行。

---

### User Story 2 - 跑挂一次不塌台，且事后查得到 (Priority: P1)

一条定时任务执行时抛了异常（模型侧报错、工具被沙箱拦下、会话归属的 Agent 已不存在……）：调度器本身不许崩，其他任务的下一次触发不许受影响；这一轮已经发生的模型调用与工具调用，照常留下可查的审计记录——钟推的账和人推的账记在同一个地方，不为定时另开一套。

**Why this priority**: 无人值守是定时任务的前提，因此"无人看着时出错会怎样"必须和触发本身一起交付。可审计是项目第一天就立下的底线，钟推不能是这条底线上的缺口。

**Independent Test**: 让处理入口在这条任务上抛异常，断言触发调用本身不外抛；随后再触发同一任务一次，断言它仍能进入处理入口——后半段专门用来证明执行权真的被释放了，而不是被永久卡死。

**Acceptance Scenarios**:

1. **Given** 一次定时触发在执行中抛异常，**When** 这次触发返回，**Then** 异常未被外抛（调度器与其余任务不受影响），错误以日志形式留痕。
2. **Given** 上一次触发刚失败过，**When** 同一条任务再次触发，**Then** 它仍能进入处理入口被完整执行（执行权已释放，没有永久卡死）。
3. **Given** 一次定时触发跑完（无论成败），**When** 查审计，**Then** 这一轮发生的模型调用与工具调用都有记录，口径与人工触发完全一致。

---

### User Story 3 - 上一次没跑完，这一次别叠着上 (Priority: P2)

一次执行比触发间隔还长（比如每分钟触发一次，但上一轮跑了三分钟）：到点时不许并发跑起第二份，也不许排队堆积——本次触发直接跳过并留一条日志。

**Why this priority**: 没有它，一个跑得慢的任务会在无人值守时越堆越多，最终把模型配额与数据库一起拖垮。它排在触发与失败隔离之后，是因为前两者不做则功能不成立、它不做则功能不可用。

**Independent Test**: 先人为占住某条任务的执行权，再触发该任务，断言处理入口完全未被调用（不排队、不叠加）；放开执行权后再触发一次，断言恢复正常执行。

**Acceptance Scenarios**:

1. **Given** 某条任务的执行权仍被上一次触发占着，**When** 触发点又到，**Then** 本次触发被跳过（处理入口零调用），并留下一条"上一次仍在跑"的可读日志，不排队等待。
2. **Given** 两条不同的定时任务，**When** 其中一条长期占着执行权，**Then** 另一条照常触发，互不影响。
3. **Given** 多实例部署的设想，**When** 审视本节的防重叠手段，**Then** 它是进程内的、不引入任何分布式协调机制（选主、分布式锁、租约）——那属于后续阶段。

---

### Edge Cases

- **触发规则非法或时区非法**：该条记错误日志并跳过，不牵连同一 Agent 的其他条目、不阻断进程启动（配置坏了要能看见，但一个坏条目不该拖垮整台）。含写法方言不对的情形——5 段 Unix 写法会被调度框架**硬拒**（实测 `Cron expression must consist of 6 fields`），MUST NOT 被当作合法输入静默按另一种解释跑起来。
- **标识与已注册任务重名**（含同一 Agent 内重复、以及两个 Agent 显式写成同一个标识）：记错误日志、跳过后者并点名两条来源，不静默取第一条（静默选择是排查成本最高的一种失败）。
- **同一条消息内容为空**：视为该条配置无效，记错误日志跳过——空消息喂给 Agent 只会白烧一轮 token。
- **一条 Agent 声明了多条定时任务**：各条独立注册、独立执行权、独立失败；一条跑挂不影响另一条（含它们共用的那个调度器）。
- **触发时所属 Agent 已不在注册表里**：处理入口抛出的异常按失败隔离处理（记日志、不崩、释放执行权）。
- **进程重启**：按配置重新注册一遍，不依赖任何持久化状态（任务状态与执行历史的持久化是后续阶段的事）。
- **同一次触发跨越零点/时区切换**：以调度器给出的那个触发时刻触发一次，不做补跑（补跑与重试是后续阶段的事）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 让定时任务的触发规则、时区、到点发给 Agent 的消息内容在 Agent 配置里声明；给一个 Agent 加一条定时任务 MUST NOT 要求改代码或重新编译。
- **FR-002**: 系统 MUST 在进程启动时扫描所有已加载 Agent 的定时配置并逐条注册进调度器；注册内容 MUST 来自配置，MUST NOT 使用编译期写死的静态调度注解。
- **FR-003**: 每条定时任务 MUST 可显式指定时区，且触发规则 MUST 与该时区一并交给调度器；未指定时区时 MUST 按服务器系统时区运行。
- **FR-004**: 每条定时任务 MUST 有一个标识：配置里可显式声明；未声明时 MUST 按"Agent 名 + 条目序号"派生。标识 MUST 在**进程内全体已注册任务**范围内唯一（执行权按标识分配，跨 Agent 重名会让两条毫不相干的任务互相挡掉下一次触发）：注册时发现与已注册任一条重名，MUST 记错误日志、跳过后者并点名两条来源，MUST NOT 静默选择。
- **FR-005**: 同一任务上一次执行尚未结束时，下一次触发点到达 MUST 直接跳过本次（处理入口零调用、不排队、不堆积）；不同任务之间 MUST 互不影响。该防重叠 MUST 是进程内的，系统 MUST NOT 为此引入选主、分布式锁或租约。跳过判定 MUST 在触发被交付执行的那一刻做出（判定执行权是否空闲），MUST NOT 采用"排队等上一次结束再执行"的语义。调度层的执行线程容量 MUST 保证不同任务之间不因彼此排队而互相推迟。
- **FR-006**: 定时触发 MUST 复用与 CLI / Web 完全相同的处理入口；定时模块 MUST NOT 感知或干预其后的循环、工具执行与模型调用。
- **FR-007**: 定时触发 MUST 落到会话上，且历次触发复用同一会话：渠道与用户固定为定时专用身份、Agent 名取该任务所属 Agent。会话标识的拼接 MUST 沿用既有唯一位置，定时模块 MUST NOT 自行拼接。
- **FR-008**: 单次定时执行失败时，系统 MUST 只记日志：MUST NOT 外抛、MUST NOT 让调度器崩溃或影响其他任务的下一次触发；无论成功失败，该次执行占用的执行权 MUST 被释放。
- **FR-009**: 定时触发的那一轮处理，其模型调用与工具调用 MUST 照常写入既有审计记录；系统 MUST NOT 为定时触发新增独立审计通路或数据表。
- **FR-010**: 配置里触发规则非法、时区非法或消息为空的条目 MUST 被记错误日志并跳过，MUST NOT 影响同一 Agent 的其他条目、其他 Agent 的任务或进程启动。
- **FR-011**: 本节 MUST NOT 引入新的第三方依赖、新的数据表与新的对外接口（HTTP 端点 / 命令行子命令）——定时是引擎内部的一条触发路径。
- **FR-012**: 本节 MUST NOT 改动前序节交付的对外契约：Agent 配置的结构与加载器、统一处理入口、会话管理器的既有成员签名与语义一处不改（为"启动时扫一遍所有已加载 Agent"而新增的只读遍历方法除外，它不改动任何既有成员）。

### Key Entities

- **定时任务定义**：一条定时配置的四项内容——触发规则（标准 cron 表达式）、时区（可空，空则随服务器）、到点发给 Agent 的消息内容、标识（可空，空则按 Agent 名 + 序号派生）。
- **执行权**：某个任务标识维度上"当前有一次执行正在进行"的状态，进程内、随任务标识分配；拿不到即跳过本次触发，无论成败都在执行结束时释放。
- **钟推会话**：渠道与用户固定为定时专用身份、Agent 名为任务所属 Agent 的那条会话；同一任务的历次触发共用它，历史上限沿用既有的对话历史上限。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在配置里声明一条定时任务后，进程常驻期间到点自动跑完一轮并留下审计记录，全程零人工介入；改触发时间只需改配置、不重新编译（一处配置改动 + 一次重启即生效）。
- **SC-002**: 注册保真：交给调度器的触发规则与时区同配置逐字一致——用参数捕获断言，两条断言全过。
- **SC-003**: 防重叠有效：占着执行权时再度触发，处理入口被调用次数为 0（既非排队、也非并行）；放开后可正常执行。
- **SC-004**: 失败隔离 + 执行权释放：一次抛异常的触发不外抛；随后同一任务仍能进入处理入口（"二进宫"式断言）——专抓"忘记释放执行权"这类只在第二次触发才现形的缺陷。
- **SC-005**: 会话身份稳定：同一任务的两次触发拿到同一会话；且会话标识的拼接仍只发生在既有那一处（全库检索无第二处拼接）。
- **SC-006**: 钟推的账与人推同口径：定时触发的那一轮，模型调用与工具调用在既有审计记录中可查，无新增审计通路。
- **SC-007**: 前序各节的测试零断言删改、零用例跳过，本节交付时全量构建门禁（含静态检查与安全检查）全绿。
- **SC-008**: 新概念引入数为零：无新数据表、无新 HTTP 端点、无新命令行子命令、无新第三方依赖（四类均为 0）。
- **SC-009**: 坏配置响亮可辨：一条写法方言不对（5 段）或时区不存在的定时配置被记错误日志并跳过，同一 Agent 的另一条合法任务照常注册运行——一条断言同时证明"坏条目被拒"与"不牵连邻居"。

## Assumptions

- **单实例部署**：多实例下"这条定时任务归哪个实例执行"的分布式协调（选主、分布式锁、租约）不在本节范围；本节的防重叠只保证同一进程内不重叠。任务失败后的自动重试与失败告警同样不做。
- **定义只来自配置**：定时任务的增删改一律改配置、重启生效；运行时的增删接口与任务状态/执行历史的持久化查询是后续阶段的事（本节不落任何任务状态）。
- **注册与运行模式无关**：引擎装配时即注册（见 Clarifications）。常驻模式持续调度；交互式对话是短会话，进程退出调度即停。
- **消息内容原样转交**：定时这一层只负责"到点拼一条消息交上去"，消息里的措辞与任务语义归 Agent 配置（其正文与技能）负责。
- **触发规则的方言**：采用调度框架原生的 **6 段** cron（秒 分 时 日 月 周，例：每天 09:00 = `0 0 9 * * *`），配置说明与示例按此口径写；不做 5 段 Unix 写法的兼容转换（见 Clarifications）。既有的 5 段样例字符串（本仓测试夹具里那个）不被校验、无实际语义，本节不改它。
- **一次性语义**：一个触发点执行一次，不补跑、不重试（跨零点、进程重启后错过的时间点都不回补）。
- **依赖前序节交付**：Agent 配置的加载与索引（第16节起）、统一处理入口与会话管理器（第17/18节）、审计落库（第16/17节）；调度能力用所用框架自带的调度器与 cron 触发器实现，不引入任何新依赖（FR-011）。
